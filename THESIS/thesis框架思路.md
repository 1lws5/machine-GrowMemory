# 传送带分拣控制系统 — 框架搭建思路

> 本文讲清楚项目"为什么这么搭"：每个部分的作用、与其它部分的相互作用、以及在整体中的作用。

## 一、整体定位

**一句话**：5 个功能模块各司其职，靠变量数据流串联成"识别 → 分拣 → 输出"的闭环。

不按"层级"划分（那样会逼人纠结谁在谁上面），而按**作用**水平划分——每个模块独立成立，单独看任何一个都能说清"它管什么、跟谁交互"。

## 二、五个模块的作用（各司其职）

### 1. GVL — 数据中转站
- **作用**：物理 I/O 的落点 + HMI 变量的存放处。
- 物理输入/输出（iStart、qBelt 等）用 `AT %IX/%QX` 绑定地址，谁要读写真实硬件都从这里走。
- 内部变量（计数、复位按钮）也放这里，供 HMI 显示和操作。
- `{attribute 'qualified_only'}` 强制用 `GVL.xxx` 限定名访问，避免重名冲突。
- **在整体中**：所有模块共享的数据总线，是"水管"，不是"水厂"。

### 2. PLC_PRG — 总调度
- **作用**：把各模块的输入输出接起来，让数据在各模块间流转。
- 职责只有三件事：**实例化功能块、给管脚接线、搬运数据**。
- 没有一行业务逻辑（无 IF/CASE/计时器），全是 `:=` 赋值和 `fbXxx(...)` 调用。
- **在整体中**：编排层（Orchestration），让"计划"落地。FB_Sorter 是方案，PLC_PRG 让方案真正接上物理世界。

### 3. FB_BeltControl — 管传送带
- **作用**：传送带的启动/停止/暂停逻辑。
- 用内部变量 `bRunState` 记忆运行状态（启动置 TRUE、停止置 FALSE），实现自保持。
- 暂停只影响输出（`qBelt := bRunState AND NOT iPause`），不改 bRunState——所以暂停解除后自动恢复，不用重按启动。
- 对外暴露 `bRunning` 状态，供 FB_Sorter 判断"传送带是否在运行"。
- **在整体中**：执行器之一，管"传送带"这条动作。

### 4. FB_Pusher — 管气缸
- **作用**：单个推杆"伸出 → 保压 → 回位"的时序。
- 用 CASE 步序状态机拆步骤：步序0待机 / 步序1伸出（计时保压，防物体没被推走）/ 步序2回位。
- 对外暴露 `qPush`（气缸真实得电状态）和 `bDone`（动作完成）。
- 同一类型实例化 3 次（fbPushA/B/C），各自内存独立，A 杆伸出时 B 杆可纹丝不动。
- **在整体中**：执行器之一，管"气缸"这条动作，是分拣决策的下游执行者。

### 5. FB_Sorter — 做决策
- **作用**：读颜色 → 决定推哪根杆 → 汇总推杆状态。
- 读入颜色代码（传感器已判好，PLC 只读结果），CASE 分派对应推杆触发。
- 实例化 3 个 FB_Pusher，把触发信号喂进去、把推杆真实状态 `qPush` 汇总输出。
- 设置报警锁存 + 复位、计数 + 复位、电平转脉冲（bSortDone）。
- 用 `bPause` 反控 FB_BeltControl 暂停，完成"分拣时传送带停下配合"的协作。
- **在整体中**：决策中心，是"大脑"。

## 三、相互作用（数据流）

```
传感器 ──→ GVL ──→ PLC_PRG ──→ FB_BeltControl（算 bRunning）
                                  │
                                  ├── bRunning ──→ FB_Sorter（"我在运行，你可以干活了"）
                                  │                    │
                                  │              ┌─────┴─────┐
                                  │          fbPushA/B/C（推杆实例）
                                  │                    │
                                  └── bPause ←────────┘（"我要分拣，你停一下"）

FB_Sorter 的 qPushA/B/C、计数 ──→ GVL ──→ 气缸、HMI
```

### 关键双向链路（项目亮点）

**FB_BeltControl 与 FB_Sorter 是平级协作，方向相反：**

| 链路 | 方向 | 含义 |
|------|------|------|
| `bRunning` | BeltControl → Sorter | 传送带给出"运行状态" |
| `bPause` | Sorter → BeltControl | 分拣下达"暂停指令" |

一个给状态、一个下指令。这正是"循环依赖、滞后一拍"的根源——也是理解 PLC 扫描周期执行顺序的绝佳案例。

### 触发 vs 输出的分离（重要设计）

FB_Sorter 内部把"触发"和"输出"拆成两类变量：

| 变量 | 语义 | 流向 |
|------|------|------|
| `bTriggerA/B/C` | "要不要干活"的触发指令 | 喂给 fbPushX.bTrigger |
| `qPushA/B/C` | 气缸"此刻得电状态" | 来自 fbPushX.qPush |

```
颜色 → bTriggerX → fbPushX.bTrigger → 状态机算 qPush → qPushX → GVL → 气缸
```

气缸接的是**推杆真实状态**（伸出 TRUE / 回位 FALSE），不是粗粒度的触发标记，FB_Pusher 的时序才真正生效。

## 四、整体作用

1. 传感器信号经 GVL 进 PLC_PRG，PLC_PRG 分发给各功能块处理。
2. FB_Sorter 做颜色决策，指挥 FB_Pusher 推杆，同时用 bPause 反控 FB_BeltControl 暂停。
3. 处理结果（推杆状态、计数）再经 GVL 输出到气缸和 HMI。

**一句话总结**：5 个模块各司其职（中转 / 调度 / 管带 / 管缸 / 决策），靠变量数据流串联成闭环。

## 五、关键设计点

1. **编排层**：PLC_PRG 只造实例 + 接线 + 搬运数据，业务逻辑全在功能块里。
2. **触发/输出分离**：bTrigger（指令）与 qPush（状态）两码事，避免时序错乱。
3. **bRunning/bPause 双向协作**：平级模块互相给状态、下指令，体现扫描周期顺序。
4. **电平转脉冲**：bDoneLatch（电平）经 R_TRIG 压成 bSortDone（脉冲），供上层做"完成事件"通知。
5. **CASE 状态机**：单整数 iStep 表达多状态，比多个布尔标志更清晰、不易出 bug。
6. **简化 vs 真实**：当前"暂停分拣"是教学简化；真实是连续运行（on-the-fly）+ 编码器物体跟踪（详见需求文档进阶版）。
